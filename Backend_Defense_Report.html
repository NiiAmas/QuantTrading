3. The AI Trading Engine (Orchestration)

The core of the backend is not just responding to HTTP requests, but actively trading in the background. I built bot_engine.py to act as the autonomous orchestrator.

📂 Backend/ ├── bot_engine.py — Main infinite loop (runs 24/7) ├── ai_analysis.py — FinBERT lazy loading & sentiment scoring ├── trade_executor.py — 3-Layer verification logic & DB entry ├── data_ingestion.py — Fetches news from NewsAPI and RSS

Deep Dive: The Multi-Speed Loop

If the bot checked the News APIs every 60 seconds, we would get permanently banned for rate-limiting. I engineered a multi-speed timing architecture to solve this.

# Inside bot_engine.py main loop
while True:
    now = time.time()

    # FAST LOOP: Price check + Stop-Loss monitor (Every 60 seconds)
    price_check_cycle()

    # MEDIUM LOOP: Trade Execution (Every 5 minutes)
    if now - _last_trade_exec >= 300:
        trade_execution_cycle()
        _last_trade_exec = now

    # SLOW LOOP: News Fetching + FinBERT AI (Every 15 minutes)
    if now - _last_news_ai >= 900:
        news_ai_cycle()
        trade_execution_cycle() # Immediately execute new signals
        _last_news_ai = now
        
    time.sleep(60)

Code Defense: This infinite loop staggers resource-heavy operations. The Fast Loop ensures we never miss a stop-loss (executing every minute). The Slow Loop only hits the NewsAPI every 15 minutes, fetching a maximum of 5 rotating symbols per cycle to guarantee we stay completely under the free-tier rate limits.

4. FinBERT & 3-Layer Verification

FinBERT Lazy Loading

FinBERT is a 2GB model. If I loaded it globally on server startup, the server would crash from out-of-memory errors before the APIs even booted.

# Inside ai_analysis.py
def _load_model():
    global _tokenizer, _model, _model_loaded
    if _model_loaded: return
    
    _tokenizer = AutoTokenizer.from_pretrained("ProsusAI/finbert")
    _model = AutoModelForSequenceClassification.from_pretrained("ProsusAI/finbert")
    _model.eval()  # Disables dropout for faster inference
    
    _model_loaded = True

Code Defense: The _load_model() function is only called when the very first news article needs analysis. Furthermore, setting _model.eval() puts the PyTorch tensors into Evaluation Mode. This disables gradient calculations (which are only needed when training AI), massively speeding up the AI's response time and saving server RAM.

The 3-Layer Verification Gate

Before any AI signal becomes a real trade, I routed it through my custom verification engine in trade_executor.py.

  1. Layer 1 (Technical): Uses NumPy to calculate RSI, MACD, and Bollinger Bands.
  2. Layer 2 (Sentiment): The FinBERT NLP probability output.
  3. Layer 3 (Quantitative): Uses standard deviation to calculate Volatility and Sharpe ratios.

The system requires at least 2 out of the 3 layers to agree before a database insertion is allowed. This mathematically eliminated false positives caused by AI hallucinations.

6. Cloud Infrastructure & Deployment

I didn't just write code; I put it live on the internet using professional DevOps practices.

Docker & Docker Compose

To avoid "It works on my machine" syndrome, I containerized the entire stack.

# Inside docker-compose.yml
services:
  backend:
    build: .
    restart: always
    ports:
      - "8000:8000"
    depends_on:
      db:
        condition: service_healthy

Code Defense: This YAML file orchestrates our servers. restart: always ensures that if the Python bot crashes due to an out-of-memory error, Docker will automatically reboot it within seconds. The depends_on block ensures the Python server waits for the PostgreSQL database to fully boot up before trying to connect, preventing race conditions.

The Deployment Script

I wrote a bash script (deploy.sh) to automate CI/CD updates on the live server.

#!/bin/bash
# Rebuild containers in the background without downtime
docker-compose up --build -d

# Prune old images to save disk space
docker image prune -f

When the team needed to push an update, I simply ran this SSH command from my terminal:

ssh root@188.166.155.154 "cd /root/QuantTrading && bash deploy.sh"

7. Critical Challenges & Solutions

The ChallengeThe Engineering Solution
API Rate Limit Bans
We were using the free tier of NewsAPI (100 requests per day). In Version 1.0, the bot requested news for all 26 symbols every 15 minutes, exhausting our entire daily quota in less than an hour.		 Resolved
I engineered a Symbol Rotation algorithm. The bot now takes the list of 26 symbols, slices it, and only analyzes 5 symbols per cycle. It takes ~1 hour to loop through all symbols, perfectly pacing our requests to stay under 100 per day. I also built a fallback system to scrape free RSS feeds if the API fails.
Zombie Python Processes
During development, when I pressed Ctrl+C to kill the server, the Uvicorn web server died, but the background bot_engine.py loop kept running in the background as an orphaned zombie process, secretly placing duplicate trades.		 Resolved
I implemented supervisord.conf inside our Docker container. Supervisor acts as a master process manager that strictly binds the FastAPI server and the Bot Engine together. If one process receives a kill signal, Supervisor ensures the other is violently terminated, preventing rogue bot trading.
