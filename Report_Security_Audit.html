✅ Implemented: Password Hashing (bcrypt)

🔐 Bcrypt Password Hashing

✅ Active & Secure

What it does: When a user registers, their plain-text password is NEVER stored in the database. Instead, it's hashed using the bcrypt algorithm, which produces a one-way, irreversible hash. Even if an attacker steals the entire database, they cannot reverse-engineer passwords from the hashes.

Where It's Implemented

# main.py
from passlib.context import CryptContext
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

# During registration:
hashed = pwd_context.hash(password)
# "password123" → "$2b$12$eImiTXuWVxfM37uY4JANjOe5q8MtDe..."

# During login:
is_valid = pwd_context.verify(password, user.hashed_password)
# Returns True if password matches, False otherwise

Why Bcrypt Is Superior

  • Intentionally slow: Bcrypt uses a "cost factor" (default 12, meaning 2^12 = 4,096 iterations). This makes each hash take ~250ms. An attacker trying 1 billion password guesses would need ~8 years.
  • Automatic salting: Each password hash includes a random salt, so two users with the same password get different hashes. This defeats rainbow table attacks.
  • Industry standard: Used by GitHub, Dropbox, and most banks. OWASP recommends bcrypt as one of the top 3 password hashing algorithms.

Attack Scenario Prevented

If an attacker gains read access to the database (SQL injection on another service, leaked backup), they see hashed passwords like $2b$12$eImiTX.... Without the original password, they can't log in. Without bcrypt, they'd see password123 in plain text.

✅ Implemented: JWT Authentication

🎫 JSON Web Token (JWT) Session Management

✅ Active & Secure

What it does: After login, the backend creates a cryptographically signed JWT token containing the user's identity and expiration date. The frontend stores this token and sends it with every API request. The backend verifies the signature on each request — no database lookup needed for session validation.

Where It's Implemented

# Token creation (backend — main.py)
from jose import jwt
SECRET_KEY = "your-secret-key-here"

def create_access_token(data: dict):
    to_encode = data.copy()
    expire = datetime.utcnow() + timedelta(days=30)
    to_encode.update({"exp": expire})
    return jwt.encode(to_encode, SECRET_KEY, algorithm="HS256")

# Token verification (on every protected request)
def get_current_user(token = Depends(oauth2_scheme)):
    payload = jwt.decode(token, SECRET_KEY, algorithms=["HS256"])
    email = payload.get("sub")    # Extract user email
    user = db.query(User).filter(User.email == email).first()
    return user

Security Properties

  • Tamper-proof: The token is signed with HS256 (HMAC-SHA256). If an attacker modifies any part of the token (e.g., changes the email or extends the expiry), the signature becomes invalid and the backend rejects it.
  • Stateless: The server doesn't store sessions in a database. Verification happens purely by checking the cryptographic signature. This is more scalable and eliminates session fixation attacks.
  • Auto-expiry: Tokens expire after 30 days. After expiry, the user must re-authenticate. This limits the damage window if a token is stolen.
  • Bearer scheme: Tokens are sent in the Authorization: Bearer {token} header, following the OAuth2 standard. Not in cookies — immune to CSRF attacks.

✅ Implemented: SQL Injection Prevention

🛡️ Parameterized Queries via SQLAlchemy ORM

✅ Active & Secure

What it does: SQL injection is the #1 web application vulnerability (OWASP Top 10). It occurs when user input is directly concatenated into SQL queries. Our SQLAlchemy ORM automatically parameterizes all queries, making SQL injection impossible through normal code paths.

How Our Code Is Protected

# ❌ VULNERABLE (raw SQL — we DON'T do this for user input):
query = f"SELECT * FROM users WHERE email = '{user_input}'"
# An attacker enters: ' OR '1'='1' --
# Query becomes: SELECT * FROM users WHERE email = '' OR '1'='1' --'
# This returns ALL users!

# ✅ SAFE (SQLAlchemy ORM — what we DO):
user = session.query(User).filter(User.email == user_input).first()
# SQLAlchemy generates: SELECT * FROM users WHERE email = $1
# With parameter: $1 = "' OR '1'='1' --"
# The malicious input is treated as a literal string, not SQL code

Everywhere It's Applied

  • main.py — All user-facing queries (login, accounts, trades) use ORM
  • bot_engine.py — All database reads/writes use ORM
  • trade_executor.py — Trade insertion and updates use ORM
  • data_ingestion.py — News article storage uses ORM

One Exception to Note

# fix_db.py and migrate_db.py use raw SQL:
conn.execute(text("DROP TABLE IF EXISTS trades CASCADE;"))
conn.execute(text("ALTER TABLE accounts ADD COLUMN sectors TEXT;"))

These migration scripts use raw SQL, but they are admin-only tools run manually — never exposed to user input. No user request can trigger these queries.

✅ Implemented: Environment Variable Secrets

🔑 Secrets Stored in .env Files

✅ Active

What it does: Sensitive configuration (database credentials, API keys, SMTP passwords) are stored in .env files, not hard-coded in source code. The python-dotenv library loads these at runtime.

Secrets Managed This Way

  • DB_USER, DB_PASS — PostgreSQL credentials
  • NEWS_API_KEY — NewsAPI access key
  • SMTP_EMAIL, SMTP_PASSWORD — Email report credentials
  • SECRET_KEY — JWT signing key (in production)

Why This Matters

If API keys were hard-coded in main.py, anyone with repository access (including your teammates) could see and misuse them. Environment variables keep secrets separate from code, following the "12-Factor App" methodology.

✅ Implemented: CORS Protection

🌐 Cross-Origin Resource Sharing (CORS)

⚠️ Partially Configured

What it does: CORS controls which websites can make API requests to our backend. Without it, any random website could send requests to our API using a visitor's browser.

Current Configuration

app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],          # ⚠️ Allows ALL origins
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)

What Should Be Improved

allow_origins=["*"] means ANY website can call our API. In production, this should be restricted:

# ✅ Production-grade CORS:
app.add_middleware(
    CORSMiddleware,
    allow_origins=[
        "https://yourdomain.com",
        "http://localhost:5173",   # Dev only
    ],
    allow_credentials=True,
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
)

Risk level: LOW. Since we use JWT Bearer tokens (not cookies), CORS being open doesn't allow unauthorized access — attackers still need a valid JWT. But restricting it is best practice.

✅ Implemented: Input Validation (Pydantic)

✅ Request Data Validation

✅ Active

What it does: FastAPI uses Pydantic to validate all incoming request data. If a field is the wrong type (e.g., string where a number is expected) or missing, FastAPI automatically returns a 422 Validation Error before our code even runs.

Example: If someone sends {"balance": "hacked"} to POST /accounts, Pydantic rejects it because balance must be a number, not a string. This prevents type confusion attacks and ensures data integrity.

🔗 Third-Party Authentication

✅ Active

What it does: Users can sign in with their existing Google account. Google handles the password verification — we never see their Google password. We receive a verified email address through Google's OAuth 2.0 protocol.

✅ Implemented: Docker Container Isolation

📦 Container-Based Deployment

✅ Active

What it does: Each service (backend, database, frontend) runs in its own isolated Docker container. If the backend is compromised, the attacker is trapped inside the container — they can't access the host operating system or other containers directly.

Security Properties

  • Process isolation: The backend container can't see processes running on the host or in other containers
  • Network isolation: Containers communicate through a Docker network. The database (port 5432) is only accessible to the backend container, not to the internet
  • Filesystem isolation: Each container has its own filesystem. A compromised backend can't read files from the host
  • Reproducibility: The exact same versions of Python, libraries, and system packages run in dev and production, preventing "works on my machine" security gaps

⚠️ Vulnerability: .env Files Were in Git

🚨 Secret Exposure via Version Control

🚨 Fixed

What happened: The .env and .env.production files were committed to Git and pushed to GitHub. These files contained the NewsAPI key, database credentials, and potentially SMTP passwords. Even on a private repository, this is a security risk because:

  • Any collaborator (current or future) can see the credentials
  • If the repo ever becomes public (accidentally or intentionally), all secrets are instantly exposed
  • Git history is permanent — even after deleting the files, they remain in past commits

What Was Fixed

# 1. Created .gitignore to prevent future tracking
.env
.env.*
!.env.example
__pycache__/
*.log
*.csv

# 2. Removed tracked files from Git (without deleting locally)
git rm --cached .env .env.production

# 3. Created .env.example (safe template for teammates)
DB_USER=your_db_username
NEWS_API_KEY=your_newsapi_key_here

Remaining Risk

The old commits still contain the secrets. To fully remove them from Git history, you would need to use git filter-branch or BFG Repo-Cleaner. However, for a student project on a private repo, this is acceptable. The immediate priority was preventing future leaks, which is now done.

Recommended Action: Rotate the NewsAPI Key

Since the key 4870e71a... was exposed, it's best practice to regenerate it on newsapi.org and update your local .env file. An exposed API key can be used by anyone to consume your quota.

🔧 Recommendation: HTTPS / TLS Encryption

🔒 Encrypt All Network Traffic

❌ Not Implemented

What's missing: Currently, our server communicates over plain HTTP (port 80). All data — including JWT tokens, user emails, and API responses — travels unencrypted. Anyone on the same network (e.g., public WiFi) can intercept and read this traffic.

Why It Matters

  • Token theft: JWT tokens sent over HTTP can be intercepted. An attacker who captures a token can impersonate the user for 30 days.
  • Data exposure: Portfolio values, trade data, and personal information are readable in transit.
  • Google OAuth requirement: Google's OAuth 2.0 policies will eventually require HTTPS for the redirect URI in production.

How to Implement (with Let's Encrypt — Free)

# 1. Install Certbot
sudo apt install certbot python3-certbot-nginx

# 2. Get a free SSL certificate (requires a domain name)
sudo certbot --nginx -d yourdomain.com

# 3. Auto-renewal (certificates expire every 90 days)
sudo certbot renew --dry-run

Is This Required for Our Project?

For production with real users: YES, absolutely required. For a student project defense demonstration: Not strictly necessary, but mentioning "we would add HTTPS via Let's Encrypt for production" shows security awareness and earns points.

Risk Level:
HIGH — Required for production

🔧 Recommendation: Rate Limiting

🚦 Prevent Brute-Force & API Abuse

❌ Not Implemented

What's missing: There's no limit on how many API requests a client can make. An attacker could send thousands of login attempts per second to brute-force passwords, or flood the /explorer endpoint to exhaust our yfinance rate limit.

How to Implement

# Install: pip install slowapi
from slowapi import Limiter
from slowapi.util import get_remote_address

limiter = Limiter(key_func=get_remote_address)

@app.post("/auth/login")
@limiter.limit("5/minute")   # Max 5 login attempts per minute per IP
def login(request: Request, form: OAuth2PasswordRequestForm):
    ...

@app.get("/explorer")
@limiter.limit("30/minute")  # Max 30 price checks per minute per IP
def get_explorer():
    ...

Is This Required?

For production: YES. Without rate limiting, a single attacker can take down the entire API or brute-force every user's password. For a student project defense: implementing this is relatively easy (10 lines of code) and demonstrates awareness of denial-of-service attacks. Highly recommended for extra points.

Risk Level:
MEDIUM — Easy to add, high impact

🔧 Recommendation: XSS Prevention

🕸️ Cross-Site Scripting (XSS) Protection

⚠️ Partially Protected

Current state: React automatically escapes content rendered with JSX ({variable}), which prevents most XSS attacks. However, using dangerouslySetInnerHTML anywhere would bypass this protection. We don't currently use it, which is good.

Where We're Protected

// React auto-escapes this — SAFE:
<p>{article.headline}</p>
// If headline = "<script>alert('hacked')</script>"
// React renders it as text, NOT as executable code

// This would be DANGEROUS (we don't do this):
<div dangerouslySetInnerHTML={{__html: article.headline}} />

Additional Protection (Recommended)

Set the Content-Security-Policy header in nginx to prevent inline scripts entirely:

# nginx.conf
add_header Content-Security-Policy "default-src 'self'; script-src 'self' https://accounts.google.com;";

Is This Required?

React's built-in escaping handles 95% of XSS. Adding CSP headers via nginx is a defense-in-depth measure. For a student project: mentioning "React auto-escapes JSX output, preventing XSS" in your defense is sufficient. Adding CSP headers is a bonus.

🔧 Recommendation: CSRF Protection

🛡️ Cross-Site Request Forgery (CSRF)

ℹ️ Not Required for Our Architecture

What CSRF is: An attacker tricks a logged-in user into submitting a malicious request by embedding a hidden form on a malicious website. When the user visits the malicious page, their browser automatically sends their session cookie to our server.

Why We're Already Protected

CSRF attacks rely on cookies being sent automatically. Our system uses JWT tokens sent in the Authorization header, NOT cookies. A malicious website can't read our JWT from localStorage or set the Authorization header — the browser's Same-Origin Policy prevents this.

Is This Required?

No. Our JWT-based authentication architecture is inherently immune to CSRF. This is one of the advantages of token-based auth over cookie-based sessions. No additional implementation needed.

🔧 Recommendation: Security HTTP Headers

🔧 Add Protective Response Headers

❌ Not Implemented

What's missing: Our nginx and FastAPI responses don't include security headers that browsers use to enforce protections.

Recommended Headers to Add in nginx.conf

# Prevent the browser from MIME-sniffing
add_header X-Content-Type-Options "nosniff" always;

# Prevent clickjacking (embedding our site in an iframe)
add_header X-Frame-Options "DENY" always;

# Enable XSS filter in older browsers
add_header X-XSS-Protection "1; mode=block" always;

# Control what info is sent in the Referer header
add_header Referrer-Policy "strict-origin-when-cross-origin" always;

# Prevent our site from being embedded in iframes
add_header Content-Security-Policy "frame-ancestors 'none';" always;

Is This Required?

Medium priority. These headers are standard security best practices. Adding them to nginx.conf takes 5 minutes and shows security maturity. Recommended for extra defense points — very easy to implement.

Defense Q&A — How to Talk About Security

Common Security Questions & Perfect Answers

Q: "How do you store user passwords?"

A: We never store plain-text passwords. Every password is hashed using bcrypt with a cost factor of 12, meaning 4,096 rounds of key derivation. Bcrypt automatically generates a unique random salt for each password, so even identical passwords produce different hashes. This defeats rainbow table attacks and makes brute-force infeasible — each guess takes ~250ms, requiring approximately 8 years to try 1 billion guesses.

Q: "How does your authentication work?"

A: We use a JWT (JSON Web Token) stateless authentication system. After successful login, the backend signs a token with HS256 containing the user's email and a 30-day expiration. The frontend stores this in localStorage and sends it as a Bearer token in every API request. The backend verifies the cryptographic signature without needing to look up a session database, making it both secure and scalable. We also support Google OAuth 2.0 as an alternative login method.

Q: "What about SQL injection?"

A: We use SQLAlchemy ORM throughout the entire application, which automatically parameterizes all database queries. User input is never concatenated into SQL strings — it's always passed as bound parameters. This makes SQL injection impossible through our application code. The only raw SQL in our project exists in admin-only migration scripts that are never exposed to user input.

Q: "What security improvements would you make for production?"

A: Three key improvements: First, HTTPS via Let's Encrypt to encrypt all network traffic and prevent token interception. Second, rate limiting using the slowapi library to prevent brute-force login attacks and API abuse. Third, security HTTP headers (X-Content-Type-Options, X-Frame-Options, Content-Security-Policy) in nginx to harden the browser-side attack surface. We've documented these in our security audit with exact implementation code ready to deploy.
