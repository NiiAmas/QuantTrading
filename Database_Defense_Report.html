1. Role Overview & Responsibilities

As the Database Architect, my mandate was to design the foundational data structures that house the entire application. Financial trading platforms require absolute precision. If a database transaction fails halfway through, a user could be charged for a trade but never receive the asset. I was responsible for ensuring strict ACID compliance (Atomicity, Consistency, Isolation, Durability) across all 7 schemas.

My core responsibilities included:

  • Designing the Entity-Relationship (ER) models for Users, Accounts, Trades, Assets, and AI Signals.
  • Configuring SQLAlchemy Object-Relational Mapper (ORM) to prevent SQL Injection attacks.
  • Optimizing database performance via Connection Pooling so the AI bot can query prices thousands of times a day without crashing the server.
  • Writing Python migration scripts to cleanly wipe corrupted tables and rebuild ledgers dynamically.
  • Configuring Docker Volumes to ensure data persistence across server reboots and deployments.

2. Technology Stack & Libraries

I selected highly reliable relational database technologies over NoSQL variants specifically for their strict schema enforcement.

Library / TechVersionSpecific Purpose & Justification
PostgreSQL14 (Alpine)The industry standard for financial databases. Chosen over MongoDB (NoSQL) because we require strict Foreign Key relationships (e.g., A Trade cannot exist without an Account).
SQLAlchemy2.0.41Python's most powerful ORM. It allows the Backend Engineer to write queries using Python classes (like session.query(Trade).all()) instead of writing raw SQL strings, which drastically reduces security vulnerabilities.
Psycopg22.9.10The actual database driver/adapter. SQLAlchemy is the steering wheel, but Psycopg2 is the engine that executes the C-level instructions against the Postgres server.
Docker Volumes-Used to map the /var/lib/postgresql/data folder inside the container to the physical hard drive of the DigitalOcean server, ensuring our database is never erased when the container reboots.

Deep Dive: The Trade Schema

The Trade table is the most heavily modified table in the database. The AI Bot engine updates the current_price and pnl_dollars of every open trade every 60 seconds.

# Inside init_db.py
class Trade(Base):
    __tablename__ = "trades"
    id = Column(Integer, primary_key=True, index=True)
    account_id = Column(Integer, ForeignKey("accounts.id"))
    symbol = Column(String, index=True)
    trade_type = Column(String)                      # "Long" or "Short"
    status = Column(String, default="Open")          # "Open" or "Closed"
    entry_price = Column(Float)
    take_profit_price = Column(Float, nullable=True) # Limits
    pnl_dollars = Column(Float, default=0.0)         # Real-time equity tracking
    signal_id = Column(Integer, nullable=True)       # Link to AI reasoning

Code Defense: The ForeignKey("accounts.id") is critical. It creates a strict relational constraint. If an account is deleted, PostgreSQL will automatically cascade-delete all trades associated with it. The index=True on the symbol column creates a B-Tree index, which speeds up search queries for specific ticker symbols by over 100x compared to a sequential table scan.

4. Connection Pooling & Performance

Because the AI Bot engine runs a 60-second infinite loop, it hits the database thousands of times a day. If I simply opened a new database connection for every request, the PostgreSQL server would run out of memory and crash (a classic TCP exhaustion attack).

# Inside database.py
engine = create_engine(
    DATABASE_URL,
    pool_size=10,         # Keep 10 connections ready at all times
    max_overflow=20,      # Allow up to 20 extra connections during peak load
    pool_pre_ping=True,   # Verify connections are alive before using them
    pool_recycle=300,     # Recycle connections every 5 min to avoid stale connections
)

Code Defense: Connection Pooling is the most important optimization in this file. pool_size=10 creates 10 permanent, reusable "tunnels" to the database. When the Backend Engineer runs a query, they simply "borrow" an existing tunnel, drastically reducing latency. pool_recycle=300 ensures that dead or timed-out connections are silently replaced every 5 minutes, ensuring 24/7 stability.

5. Cross-Role Collaboration

🤝 Correlating with the Backend Engineer

The Backend Engineer built the FinBERT AI, but AI is useless without memory. I designed the TradeSignal table specifically for them.

  • The AI Handshake: When FinBERT finishes analyzing an article, the Backend Engineer inserts a row into my TradeSignal table containing the "BUY" or "SELL" recommendation, with the boolean flag executed = False.
  • The Executor Pickup: Five minutes later, the Backend's Trade Executor loop queries my table looking for executed == False. This database flag is the literal bridge that allows the AI module and the execution module to talk to each other asynchronously.

🤝 Correlating with the Frontend Developer

The Frontend Developer was struggling to build the stacked "Realized vs Unrealized" layout on the Dashboard because they were trying to calculate math in React. I solved this at the Database level.

  • Data Separation: I explained my schema design to them. The Account.balance is strictly "Available Cash". The Trade.pnl_dollars is strictly "Unrealized Equity" (if the trade status is 'Open'). By separating these fields structurally, the Backend could easily sum them up and serve distinct integers to the Frontend, allowing them to perfectly render their UI components without complex client-side math.

6. Data Migrations & Integrity Recovery

During the project, we discovered a logical bug: The bot was buying "Short" positions, but the system was trying to add them to the PortfolioAssets holding table. You cannot physically "hold" a shorted stock. The table became corrupted with negative shares.

The Migration Script (reset_portfolio.py)

I couldn't just delete the database—we had live user accounts. I had to write a Python surgical script to wipe only the corrupted table and recalculate the ledgers dynamically.

# Inside reset_portfolio.py
# 1. Safely wipe the corrupted table
session.query(PortfolioAsset).delete()

# 2. Find ONLY Long, Physical trades
open_longs = session.query(Trade).filter(
    Trade.status == "Open",
    Trade.trade_type == "Long"
).all()

# 3. Rebuild the ledger mathematically
for trade in open_longs:
    asset_class = _classify_asset(trade.symbol)
    if asset_class in ("Crypto", "Stock"):
        # Create fresh, accurate asset entries
        new_asset = PortfolioAsset(
            account_id=trade.account_id,
            symbol=trade.symbol,
            shares=trade.quantity
        )
        session.add(new_asset)

Command Defense: To run this on the live production server without taking it offline, I correlated with the Systems Engineer to execute: docker exec -it quanttrading-backend-1 python3 reset_portfolio.py. This opened an interactive terminal inside the running Docker container and surgically repaired the database in milliseconds.

7. Critical Challenges & Solutions

The ChallengeThe Engineering Solution
Zombie Connections crashing PostgreSQL
During early development, the backend would crash after 2 days with the error FATAL: sorry, too many clients already. The bot was opening connections to check prices but forgetting to close them.		 Resolved
I enforced a strict try...finally block standard across the entire codebase. Every single database transaction must end with finally: session.close(). I also added pool_recycle=300 to the SQLAlchemy engine to forcefully slaughter any connections that remained idle for over 5 minutes.
Data Loss on Server Restart
Every time we pushed a new update and rebuilt the Docker containers, all user accounts and trade history were completely erased.		 Resolved
Docker containers are ephemeral (temporary) by design. I configured a Docker Volume in the docker-compose.yml file: - pgdata:/var/lib/postgresql/data. This maps the database's internal memory directly to the physical hard drive of our DigitalOcean droplet. Now, even if the container is destroyed, the data remains safely on the hard drive and reconnects upon reboot.
