2. What is the Backend? (A Layman's Overview)

If you imagine building a restaurant, the Database is the massive freezer in the basement where all the raw ingredients (data) are stored safely. The Frontend is the waiter, the dining room, and the presentation. The Backend is the kitchen staff and the head chef. I take the orders from the waiter (the APIs), I fetch the ingredients from the freezer (the ORM), I chop and cook them (the AI Analysis and Trade Execution), and I hand the finished meal back to the waiter.

The Backend Lexicon (Explained Simply)

  • FastAPI: The head chef. It is a highly-efficient Python framework that stands at the kitchen door and listens to thousands of orders (HTTP Requests) from the Frontend at exactly the same time without getting overwhelmed.
  • FinBERT (HuggingFace): The specialist chef. It is an Artificial Intelligence model that has read 10,000 financial books. I hand it a news headline, and it tells me if the news is Good (Buy) or Bad (Sell).
  • Docker: A shipping container. Instead of installing Python, PostgreSQL, and 50 libraries directly onto a cloud server (which always breaks), I put the entire kitchen inside a metal box (Docker). I can move this box to any server in the world, and it will work exactly the same way.
  • Nginx: The bouncer at the front door of the restaurant. When random people on the internet try to connect, Nginx checks if they are safe, and then secretly escorts them to the backend kitchen.

3. Library Deep Dives: Activation & Syntax

To truly understand how this project was built from scratch, we need to look at exactly how we activated and used the core technologies.

3.1 FastAPI: The Head Chef

Why we chose it: Traditional Python frameworks (like Flask or Django) do things one by one. If a user asks for a massive chart, everyone else has to wait in line. FastAPI uses asynchronous logic (async/await), allowing it to juggle thousands of requests simultaneously.

How we activated it: We opened the terminal and installed it via pip:

pip install fastapi uvicorn

The Syntax: Here is exactly how we tell FastAPI to listen for the Frontend's walkie-talkie request:

// This is a basic FastAPI Endpoint in main.py
from fastapi import FastAPI
app = FastAPI()

# This tells FastAPI: "If someone asks for /api/trades, run this function"
@app.get("/api/trades")
async def get_user_trades():
    # Go to the database freezer
    trades = fetch_trades_from_db()
    
    # Hand the meal back to the frontend
    return {"trades": trades}

3.2 FinBERT (Transformers): The AI Brain

Why we chose it: General AI models (like ChatGPT) don't understand stock markets. If a headline says "Apple is dropping", ChatGPT might think the fruit is falling. FinBERT is specifically trained on financial sentiment.

How we activated it:

pip install transformers torch

The Syntax: We have to load the model into the server's memory, give it a sentence, and ask for the probabilities.

from transformers import AutoModelForSequenceClassification, AutoTokenizer

# 1. Download the AI brain from the internet
tokenizer = AutoTokenizer.from_pretrained("ProsusAI/finbert")
model = AutoModelForSequenceClassification.from_pretrained("ProsusAI/finbert")

# 2. Give it a headline
headline = ["Tesla stock crashes 20%"]
inputs = tokenizer(headline, return_tensors="pt")

# 3. Ask for the prediction
outputs = model(**inputs)
# Outputs: [Positive: 1%, Negative: 95%, Neutral: 4%]

I then took that negative 95% and wrote a rule: "If Negative > 50%, generate a SELL signal in the database."

5. The Step-by-Step Building Process

Here is exactly how I built the Backend and Systems architecture, step by step.

Step 1: The Bot Engine (The Infinite Loop)

The system needs to trade automatically 24/7. I created bot_engine.py containing an infinite while True: loop. However, I immediately ran into a problem: API Rate Limiting.

The Problem: We use NewsAPI to get headlines. Their free tier only allows 100 requests per day. If my infinite loop checked for news every 60 seconds, we would get banned in an hour.

The Solution: I built a "Multi-Speed" architecture inside the loop:

while True:
    now = time.time()

    # 1. FAST (Every 60 seconds)
    # Check live prices and trigger Stop-Losses instantly
    price_check_cycle()

    # 2. MEDIUM (Every 5 minutes)
    # Execute any trades the AI requested
    if now - last_trade_time >= 300:
        trade_execution_cycle()

    # 3. SLOW (Every 15 minutes)
    # Fetch news for only 5 symbols at a time to avoid bans
    if now - last_news_time >= 900:
        news_ai_cycle()

By staggering the operations, the bot could react to sudden price crashes instantly (every 60s) without getting banned by the news providers (every 15m).

Step 2: Lazy Loading the AI

When I first deployed the FinBERT model to the cloud server, the server instantly crashed with an "Out of Memory" error. The 2GB model was too big to load at startup while the rest of the app was booting.

The Solution: I implemented "Lazy Loading". Instead of loading the AI at the top of the file, I put the loading code inside a function that is ONLY called when the very first news article arrives. I also added model.eval(), which turns off the "learning/training" mode of the AI, making it strictly read-only. This saved 50% of the server's RAM.

Step 3: The 3-Layer Verification Gate

I realized that AI is sometimes stupid. If a headline said "Apple releases new iPhone case", the AI might confidently say BUY, even though the actual stock price is plummeting.

I wrote the 3-Layer Verification engine in trade_executor.py:

  1. Layer 1 (Technical): I used mathematics to check RSI and MACD (is the stock currently crashing?).
  2. Layer 2 (Sentiment): The FinBERT AI score.
  3. Layer 3 (Quantitative): Risk vs Reward ratios.

I wrote a strict rule: if layers_passed < 2: return False. At least 2 of the 3 layers must agree, otherwise the trade is thrown in the trash. This mathematically eliminated false-positive AI hallucinations.

6. The Deployment Workflow (DevOps)

Once the code worked on my laptop, I had to put it on the public internet. This requires extreme security and engineering.

1. Containerization (Docker)

Instead of manually installing Python on our DigitalOcean server, I wrote a docker-compose.yml file. This acts as an instruction manual that builds a virtual "box" (container) for the Backend, and a separate box for the Database.

services:
  backend:
    build: .
    restart: always
    depends_on:
      - db

The restart: always command is a lifesaver. It means if my Python script crashes due to a random error at 3:00 AM, Docker will automatically reboot the system within two seconds without me having to wake up.

2. The Bouncer (Nginx)

You should never expose a Python web server directly to the wild internet (Port 80) because hackers will bombard it. I installed Nginx.

Nginx sits on Port 80, takes all the internet traffic, filters out the malicious requests, and then secretly funnels the legitimate requests to my Python backend hiding on Port 8000. I wrote an nginx.conf file to handle this routing seamlessly.

3. The Deployment Command (SSH)

When the team wanted to push a new update, I simply opened my terminal and executed this line:

ssh root@188.166.155.154 "cd /root/QuantTrading && bash deploy.sh"

Layman Explanation: SSH (Secure Shell) is a cryptographic protocol. It securely logs me into the remote server in New York. It navigates to our project folder, and executes a script I wrote called deploy.sh. That script tells Docker to quietly download the new code, stop the old containers, and start the new ones without any downtime.
