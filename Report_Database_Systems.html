Project Overview & Your Role as Database Architect

What the Database Does in QuantTrading

The database is the foundation of the entire system. Every piece of data — user accounts, trading portfolios, individual trades, AI signals, news articles, price history — lives in a PostgreSQL database. Without the database, the bot engine has nothing to trade with, the API has nothing to serve, and the frontend has nothing to display.

Your Role: Database & Systems Architect

As the Database Architect, you were responsible for:

  • Designing the database schema — defining all 7 tables, their columns, data types, relationships, and constraints
  • ORM model definitions — writing SQLAlchemy Python classes that map to database tables
  • Relationship design — foreign keys connecting users → accounts → trades → portfolio assets
  • Data type decisions — choosing Integer vs Float vs Text vs DateTime for each column and why
  • PostgreSQL setup — installing and configuring the database server
  • Connection pooling — configuring database.py for optimal performance
  • Migration scripts — writing fix_db.py and migrate_db.py for schema changes
  • Docker database — configuring PostgreSQL as a Docker container with persistent storage

How Your Work Connects to Other Roles

With the Backend Person: You define the table models in init_db.py. The Backend person imports your models (from init_db import User, Account, Trade, PortfolioAsset) and uses SQLAlchemy to query them. Every column name you define becomes a field they access in Python (e.g., trade.entry_price, account.balance). If you change a column name, their code breaks.

With the Frontend Person: You don't interact directly with the frontend. But every data field the user sees on screen originated from one of your database columns. When the Dashboard shows "Account Equity: $12,450.00", that value was stored in your accounts.balance column. The data flow is: Your Table → Backend Query → API JSON Response → Frontend Display.

Technology Stack — PostgreSQL, SQLAlchemy, ORM Concepts

PostgreSQL — The Database Engine

Why PostgreSQL over MySQL, SQLite, or MongoDB?

  • ACID compliance — PostgreSQL guarantees Atomicity, Consistency, Isolation, Durability. When the bot writes a trade while the API reads portfolio data simultaneously, neither operation corrupts the other.
  • MVCC (Multi-Version Concurrency Control) — PostgreSQL can handle concurrent reads and writes without locking entire tables. The bot engine and API server access the same tables simultaneously without deadlocks.
  • Rich data types — PostgreSQL supports Float, Text, DateTime, and JSON natively. We use Float for prices (precision matters in trading) and Text for flexible string storage.
  • Production-grade — Used by companies like Instagram, Spotify, and Uber. SQLite is for development only; MySQL lacks some advanced features; MongoDB is document-based which doesn't suit our relational data (users HAVE accounts WHICH HAVE trades).
  • Docker support — Official postgres:15-alpine Docker image makes deployment trivial.

SQLAlchemy 2.0 — The ORM (Object-Relational Mapper)

What is an ORM? An ORM maps database tables to Python classes and SQL queries to Python methods. Instead of writing raw SQL:

-- Raw SQL
SELECT * FROM trades WHERE account_id = 5 AND status = 'Open';

We write Python:

# SQLAlchemy ORM
session.query(Trade).filter(Trade.account_id == 5, Trade.status == "Open").all()

Benefits of ORM:

  • SQL injection protection — parameterized queries are automatic
  • Database portability — switch from PostgreSQL to MySQL by changing one URL string
  • Python-native — work with Python objects instead of raw dictionaries
  • Relationship handling — user.accounts automatically fetches related records

Key SQLAlchemy Concepts Used in Our Project

# Base — the parent class all models inherit from
from sqlalchemy.orm import declarative_base
Base = declarative_base()

# Column — defines a table column with type and constraints
Column(Integer, primary_key=True)      # Auto-incrementing ID
Column(String, nullable=False)          # Required text field
Column(Float, default=0.0)             # Decimal with default
Column(DateTime, default=datetime.utcnow)  # Auto-timestamp

# ForeignKey — creates a relationship between tables
Column(Integer, ForeignKey("users.id"))  # Points to users table

# relationship() — enables Python-level navigation
accounts = relationship("Account", back_populates="user")
# Now: user.accounts returns all Account objects for this user

database.py — The Connection Engine

database.py — How Python Connects to PostgreSQL
from sqlalchemy import create_engine
from sqlalchemy.orm import sessionmaker
from dotenv import load_dotenv
import os

load_dotenv()  # Load .env file variables

# Build connection URL from individual environment variables
DB_USER = os.getenv("DB_USER", "niiamas")
DB_PASS = os.getenv("DB_PASS", "")
DB_HOST = os.getenv("DB_HOST", "localhost")
DB_NAME = os.getenv("DB_NAME", "quant_db")

# Support full DATABASE_URL override (used by Docker)
DATABASE_URL = os.getenv("DATABASE_URL",
    f"postgresql://{DB_USER}:{DB_PASS}@{DB_HOST}/{DB_NAME}")

# Create the engine with connection pooling
engine = create_engine(
    DATABASE_URL,
    pool_size=5,          # Maintain 5 persistent connections
    max_overflow=10,      # Allow 10 extra during traffic spikes
    pool_pre_ping=True    # Verify connections are alive before using
)

# Session factory — creates database sessions for each request
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

Connection URL Anatomy

postgresql://niiamas:@localhost/quant_db
│            │       │ │         │
│            │       │ │         └─ Database name
│            │       │ └─────────── Host (localhost for dev, "db" for Docker)
│            │       └───────────── Password (empty in dev)
│            └───────────────────── Username
└────────────────────────────────── Driver (PostgreSQL)

Connection Pooling Explained

Without pooling: Every API request opens a new TCP connection to PostgreSQL (3-way handshake + authentication + query + close). With 100 requests/second, that's 100 connections opening and closing per second — massive overhead.

With pooling (pool_size=5): SQLAlchemy maintains 5 persistent connections. When the API needs a connection, it borrows one from the pool. When done, it returns it to the pool (not closed). The next request reuses the same connection instantly.

pool_pre_ping=True: Sometimes PostgreSQL restarts (server reboot, Docker container restart). Pooled connections to the old server are now "dead." Without pre-ping, the next request using a dead connection would get OperationalError. With pre-ping, SQLAlchemy sends SELECT 1 first — if the connection is dead, it silently creates a new one.

SessionLocal — The Session Factory

# autocommit=False → We control when changes are saved (explicit commit)
# autoflush=False  → Don't auto-push Python changes to SQL until we say so
# bind=engine      → Use our pooled engine for connections

Every database interaction in the backend starts with session = SessionLocal() and ends with session.close(). The session tracks all changes (INSERT, UPDATE, DELETE) and only writes them to PostgreSQL when session.commit() is called.

init_db.py — Every Table Model Defined

init_db.py — The Schema Blueprint (7 Tables)

This file defines ALL database tables as Python classes using SQLAlchemy's declarative ORM. Each class maps to one PostgreSQL table. Each class attribute maps to one column.

The Base Class

from sqlalchemy.orm import declarative_base, relationship
from sqlalchemy import Column, Integer, String, Float, DateTime, ForeignKey, Text
from datetime import datetime

Base = declarative_base()

Base is the parent class for all models. When we call Base.metadata.create_all(bind=engine), SQLAlchemy finds every class that inherits from Base and creates the corresponding table. This is why ALL models must inherit from Base.

The create_all() function at the bottom:

if __name__ == "__main__":
    from database import engine
    print("🏗️  Creating database tables...")
    Base.metadata.create_all(bind=engine)
    print("✅ All tables created successfully!")

This is the script the Database person runs to physically create all tables in PostgreSQL. create_all() is idempotent — running it multiple times is safe; it only creates tables that don't already exist.

Table 1: users — User Authentication & Identity

users table — Who can log in
class User(Base):
    __tablename__ = "users"

    id              = Column(Integer, primary_key=True, index=True)
    email           = Column(String, unique=True, index=True, nullable=False)
    hashed_password = Column(String, nullable=False)
    pin             = Column(String, nullable=True)
    created_at      = Column(DateTime, default=datetime.utcnow)

    # Relationship: one user has many accounts
    accounts = relationship("Account", back_populates="user")
Column Type Constraints Why This Type?
idIntegerPRIMARY KEY, AUTO-INCREMENT, INDEXEDEvery table needs a unique identifier. Integer is fast for joins and lookups.
emailStringUNIQUE, NOT NULL, INDEXEDUNIQUE prevents duplicate accounts. INDEXED because we search by email during every login (fast lookup). NOT NULL because a user must have an email.
hashed_passwordStringNOT NULLStores bcrypt hash (e.g., "$2b$12$eXaMpLe..."). We NEVER store plain-text passwords. String because bcrypt hashes are 60 characters.
pinStringNULLABLEOptional 4-digit security PIN. Nullable because it's optional during registration.
created_atDateTimeDEFAULT: now()Automatically records when the user registered. Useful for analytics and email reports.

Why index=True on email?

An index creates a B-tree data structure on the email column. Without it, finding a user by email requires scanning EVERY row in the table (O(n) — slow for 10,000+ users). With an index, PostgreSQL can find the user in O(log n) — essentially instant.

The relationship() Connection

accounts = relationship("Account", back_populates="user")

This creates a virtual Python attribute. After querying user = session.query(User).get(1), you can access user.accounts which automatically runs SELECT * FROM accounts WHERE user_id = 1 behind the scenes. back_populates="user" creates the reverse link — from any Account object, account.user gives you the parent User.

🤝 Coordination — Who Uses This Table?

Backend: main.py queries users during login (session.query(User).filter(User.email == email)), registration (INSERT), and Google auth. email_reports.py queries ALL users to send daily reports.

Frontend: AuthPage.jsx sends email + password to the backend, which queries this table. The frontend never sees the hashed_password column — it's filtered out by the backend.

Table 2: accounts — Trading Account Configuration

accounts table — Each user's trading portfolios
class Account(Base):
    __tablename__ = "accounts"

    id              = Column(Integer, primary_key=True, index=True)
    user_id         = Column(Integer, ForeignKey("users.id"), nullable=False)
    name            = Column(String, nullable=False)
    balance         = Column(Float, default=10000.0)
    initial_balance = Column(Float, default=10000.0)
    strategy        = Column(String, default="Moderate")
    asset_types     = Column(Text, nullable=True)
    sectors         = Column(Text, nullable=True)
    created_at      = Column(DateTime, default=datetime.utcnow)

    # Relationships
    user   = relationship("User", back_populates="accounts")
    trades = relationship("Trade", back_populates="account")
Column Type Constraints Purpose & Why This Type
idIntegerPK, AUTO-INCUnique account identifier
user_id FKIntegerFOREIGN KEY → users.id, NOT NULLLinks account to its owner. ForeignKey ensures referential integrity — you can't create an account for a non-existent user.
nameStringNOT NULLHuman-readable name like "High Risk Crypto Fund"
balanceFloatDEFAULT: 10000.0Current cash balance. Float for decimal precision. Updated when trades close (realized P&L adjusts balance).
initial_balanceFloatDEFAULT: 10000.0The starting balance. NEVER changes after creation. Used to calculate overall return percentage: (balance - initial_balance) / initial_balance × 100
strategyStringDEFAULT: "Moderate"Risk profile: "Low", "Moderate", or "Aggressive". Determines position sizing and the min_layers requirement for the 3-Layer Verification.
asset_typesTextNULLABLEJSON string of selected markets: '["Stocks", "Crypto"]'. Text instead of JSON column for simpler compatibility. Nullable because existing accounts (before this feature) don't have it.
sectorsTextNULLABLEJSON string of selected stock sectors: '["Technology", "Finance"]'. Same rationale as asset_types.

Why Two Balance Columns?

balance changes over time as trades produce gains or losses. initial_balance is frozen at creation. This dual-column design allows us to calculate returns:

return_percentage = ((account.balance - account.initial_balance) / account.initial_balance) * 100
# Example: ($12,500 - $10,000) / $10,000 × 100 = +25.0%

Without initial_balance, we'd have no way to know the starting point.

Why asset_types and sectors Are Text, Not a Separate Table

We store them as JSON strings (e.g., '["Stocks","Crypto"]') in a single Text column rather than creating a separate account_asset_types junction table. This is a deliberate denormalization — it's simpler, avoids extra JOINs, and the data is always read/written as a complete list (never queried individually).

Table 3: trades — Every Trade the Bot Makes

trades table — The complete trade ledger
class Trade(Base):
    __tablename__ = "trades"

    id            = Column(Integer, primary_key=True, index=True)
    account_id    = Column(Integer, ForeignKey("accounts.id"), nullable=False)
    symbol        = Column(String, nullable=False)
    trade_type    = Column(String, nullable=False)        # "Long" or "Short"
    entry_price   = Column(Float, nullable=False)
    current_price = Column(Float, default=0.0)
    exit_price    = Column(Float, nullable=True)
    quantity      = Column(Float, default=0.0)
    pnl           = Column(Float, default=0.0)            # Percentage P&L
    pnl_dollars   = Column(Float, default=0.0)            # Dollar P&L
    stop_loss     = Column(Float, nullable=True)
    take_profit   = Column(Float, nullable=True)
    status        = Column(String, default="Open")        # "Open" or "Closed"
    reasoning     = Column(Text, nullable=True)           # AI reasoning text
    created_at    = Column(DateTime, default=datetime.utcnow)
    closed_at     = Column(DateTime, nullable=True)

    account = relationship("Account", back_populates="trades")
Column Type Purpose & Design Decision
account_id FKIntegerLinks trade to its account. One account has many trades.
symbolStringThe ticker symbol (e.g., "AAPL", "BTC-USD", "EURUSD=X"). Matches yfinance ticker format.
trade_typeString"Long" (buy expecting price to rise) or "Short" (sell expecting price to fall). String instead of Boolean for clarity and future extensibility.
entry_priceFloatPrice when the trade was opened. Never changes after creation.
current_priceFloatLive market price. Updated every 60 seconds by the bot engine's fast cycle. Used for unrealized P&L calculations.
exit_priceFloat (nullable)Price when the trade was closed. NULL while trade is open. Set when stop-loss or take-profit is hit.
quantityFloatNumber of shares/coins. Float because crypto allows fractional amounts (e.g., 0.0123 BTC).
pnlFloatPercentage gain/loss. ((current_price - entry_price) / entry_price) × 100. Updated every price cycle.
pnl_dollarsFloatDollar gain/loss. (current_price - entry_price) × quantity. More intuitive than percentage for users.
stop_lossFloat (nullable)Price at which the bot automatically closes the trade to limit losses. Calculated using ATR × sl_mult.
take_profitFloat (nullable)Price at which the bot automatically closes the trade to lock in profits. Calculated using ATR × tp_mult.
statusString"Open" (active trade) or "Closed" (trade completed). The frontend uses this to separate the Trade Ledger into Open/Closed tabs.
reasoningTextFull AI analysis text explaining WHY this trade was made. Example: "3-LAYER VERIFIED (3/3) | ✅ TA: BULLISH | ✅ SA: BUY | ✅ QA: FAVORABLE". Text type because it can be very long. Displayed in TradeAnalysis page.
closed_atDateTime (nullable)NULL while open. Set to UTC timestamp when trade closes. Used for trade duration calculations.

Why Both pnl (%) and pnl_dollars ($)?

The frontend displays both: "+5.23% (+$523.00)". We pre-compute both on the backend during each price update rather than making the frontend calculate them. This follows the "compute once, read many" principle — the bot engine updates these once every 60 seconds, but potentially 100 frontend users read them every 5 seconds.

Table 4: portfolio_assets — Current Holdings

portfolio_assets table — What each account currently owns
class PortfolioAsset(Base):
    __tablename__ = "portfolio_assets"

    id            = Column(Integer, primary_key=True, index=True)
    account_id    = Column(Integer, ForeignKey("accounts.id"), nullable=False)
    symbol        = Column(String, nullable=False)
    shares        = Column(Float, default=0.0)
    avg_price     = Column(Float, default=0.0)
    current_price = Column(Float, default=0.0)
    asset_class   = Column(String, default="Stock")
Column Type Purpose
account_id FKIntegerWhich account owns this asset
symbolStringTicker symbol (e.g., "AAPL", "BTC-USD")
sharesFloatTotal quantity held. Increases when buying, decreases when selling. When it hits 0, the asset is no longer "held."
avg_priceFloatWeighted average purchase price across all buys. If you buy 10 shares at $100 and 10 more at $110, avg_price = $105.
current_priceFloatLatest market price. Updated every 60 seconds by the fast cycle.
asset_classString"Stock", "Crypto", "Forex", or "Commodity". Used for display categorization in the frontend.

Difference Between portfolio_assets and trades

trades records every individual transaction (buy this on Jan 5, sell half on Jan 10, buy more on Jan 15). It's a ledger — historical, immutable entries.

portfolio_assets is the current state — an aggregate view. If you made 5 separate purchases of AAPL at different prices, portfolio_assets has ONE row with total shares and weighted average price. It's like a summary card.

The bot engine maintains both: when a trade opens, it creates a Trade record AND updates the PortfolioAsset record (or creates one if it's the first purchase of that symbol).

Table 5: trade_signals — AI Signal History

trade_signals table — Log of every AI signal generated
class TradeSignal(Base):
    __tablename__ = "trade_signals"

    id         = Column(Integer, primary_key=True, index=True)
    symbol     = Column(String, nullable=False)
    signal     = Column(String, nullable=False)      # "BUY", "SELL", "HOLD"
    confidence = Column(Float, default=0.0)
    reasoning  = Column(Text, nullable=True)
    created_at = Column(DateTime, default=datetime.utcnow)

Purpose: Every time the 3-Layer Verification generates a signal (BUY, SELL, or HOLD), we log it here — even if the signal didn't result in an actual trade (e.g., signal was HOLD, or the account didn't have enough balance). This creates an audit trail for analysis.

Use case: The Backend person can query this table to analyze signal accuracy: "How many BUY signals with confidence > 0.7 actually resulted in profitable trades?" This is valuable for tuning the AI model's thresholds.

The lat/lng columns exist SOLELY for the Frontend's 3D Globe. The Database person added them because the Frontend developer needed geographic coordinates to position news markers on the globe.

Table 7: bitcoin_prices — Historical Price Cache

bitcoin_prices table — Price history cache
class BitcoinPrice(Base):
    __tablename__ = "bitcoin_prices"

    id         = Column(Integer, primary_key=True, index=True)
    price      = Column(Float, nullable=False)
    volume     = Column(Float, nullable=True)
    timestamp  = Column(DateTime, default=datetime.utcnow)

Purpose: Caches historical price data locally so we don't need to re-fetch from yfinance every time. While named "bitcoin_prices" (originally created for BTC tracking), it serves as a general price logging table.

Why cache prices? yfinance has rate limits. If the bot engine queries "3 months of AAPL history" every 5 minutes, we'd hit rate limits quickly. Instead, we cache prices locally and only fetch incremental updates.

Database Migrations — fix_db.py & migrate_db.py

fix_db.py — Nuclear Reset (DESTRUCTIVE)
def reset_tables():
    """DROP all tables and recreate from scratch. DESTROYS ALL DATA."""
    with engine.connect() as conn:
        conn.execute(text("DROP TABLE IF EXISTS trades CASCADE;"))
        conn.execute(text("DROP TABLE IF EXISTS portfolio_assets CASCADE;"))
        conn.execute(text("DROP TABLE IF EXISTS trade_signals CASCADE;"))
        conn.execute(text("DROP TABLE IF EXISTS news_articles CASCADE;"))
        conn.execute(text("DROP TABLE IF EXISTS bitcoin_prices CASCADE;"))
        conn.execute(text("DROP TABLE IF EXISTS accounts CASCADE;"))
        conn.execute(text("DROP TABLE IF EXISTS users CASCADE;"))
        conn.commit()
    
    # Re-create with current schema
    Base.metadata.create_all(bind=engine)

When to use: When schema changes are so dramatic that migration is impractical (e.g., changing a column's data type, removing columns, or restructuring relationships). This drops ALL tables and recreates them — ALL DATA IS LOST.

Why CASCADE? PostgreSQL prevents dropping a table that other tables reference via foreign keys. CASCADE says "also drop dependent tables." Without it, DROP TABLE users would fail because accounts has a ForeignKey("users.id").

Order matters: We drop child tables first (trades, portfolio_assets) before parent tables (accounts, users). This is more predictable than relying on CASCADE for everything.

migrate_db.py — Non-Destructive Migration
def migrate():
    """Add new columns without losing existing data."""
    with engine.connect() as conn:
        try:
            conn.execute(text("ALTER TABLE accounts ADD COLUMN asset_types TEXT;"))
            conn.commit()
            print("✅ Added 'asset_types' column")
        except Exception:
            conn.rollback()
            print("✅ 'asset_types' column already exists")
        
        try:
            conn.execute(text("ALTER TABLE accounts ADD COLUMN sectors TEXT;"))
            conn.commit()
            print("✅ Added 'sectors' column")
        except Exception:
            conn.rollback()
            print("✅ 'sectors' column already exists")

When to use: When adding NEW columns to existing tables. This preserves all existing data. The try/except pattern makes it idempotent — running it twice is safe because the second run catches the "column already exists" error and continues.

Why not just use fix_db.py? In production with real user data, dropping tables would delete everything. Migrations add features without data loss. This is critical for deployed systems.

🤝 Coordination — When Migrations Were Needed

The asset_types and sectors columns were added AFTER the initial deployment. The Frontend developer needed the Account Wizard to store market preferences. The Database person wrote migrate_db.py, ran it on the production server (python migrate_db.py), which added the columns without affecting existing accounts. Then the Backend person updated the POST /accounts endpoint to accept and store these new fields. Finally, the Frontend person built the wizard UI.

volumes:
  pgdata:    # Named Docker volume — survives container restarts

Key Concepts Explained

  • postgres:15-alpine — Alpine Linux variant is ~70MB (vs ~370MB for full). PostgreSQL 15 is a stable, well-tested version.
  • restart: always — If the container crashes or the server reboots, Docker automatically restarts it. Critical for a 24/7 trading system.
  • POSTGRES_USER/PASSWORD/DB — These environment variables are recognized by the official PostgreSQL image. On first start, it automatically creates the database and user.
  • volumes: pgdata — THIS IS THE MOST CRITICAL LINE. Without a volume, all database data lives inside the container. If the container is deleted (docker compose down -v), ALL DATA IS LOST. The named volume pgdata stores data on the host's filesystem, surviving container lifecycle.
  • healthcheck — pg_isready is PostgreSQL's built-in connectivity checker. The Backend service uses depends_on: db: condition: service_healthy to wait until PostgreSQL is accepting connections before starting. Without this, the Backend would crash on startup because the database isn't ready yet.

Key Defense Q&A

Common Questions & Perfect Answers

Q: "Why PostgreSQL over MongoDB?"

A: Our data is inherently relational — users HAVE accounts, accounts HAVE trades, accounts HAVE portfolio_assets. These are one-to-many relationships that PostgreSQL handles natively with foreign keys and JOINs. MongoDB is document-based, which would mean either: (a) embedding all trades inside the account document (which grows unboundedly and makes querying slow), or (b) storing them separately without referential integrity (no guarantee a trade references a real account). PostgreSQL's ACID transactions also ensure that when we simultaneously update a trade's P&L and the account's balance, either BOTH succeed or NEITHER does — critical for financial data consistency.

Q: "Why Float for prices instead of Decimal?"

A: Float was chosen for simplicity and performance. In a production trading system handling real money, we would use Numeric(precision=10, scale=2) to avoid floating-point rounding errors (e.g., $0.1 + $0.2 = $0.30000000000000004 in IEEE 754 floats). However, since this is a simulated trading platform, the minor rounding differences (fractions of a cent) don't affect our results, and Float arithmetic is 2-3x faster than Decimal operations.

Q: "Explain the relationship between trades and portfolio_assets."

A: They serve different purposes. trades is a complete, immutable ledger of every transaction — every buy, every sell, with timestamps, entry/exit prices, and P&L. portfolio_assets is a live summary showing what the account currently owns. When the bot buys 10 shares of AAPL at $150, it creates a Trade record (ledger entry) AND either creates or updates a PortfolioAsset record (summary). If the account already held 5 shares of AAPL at $140, the PortfolioAsset updates to: shares=15, avg_price=($140×5 + $150×10)/15 = $146.67. When the bot sells all 15 shares, the Trade records the sale, PortfolioAsset sets shares=0, and the account balance increases by the realized profit.

Q: "How do you handle database migrations in production?"

A: We have two migration tools. For non-destructive changes (adding new columns), we use migrate_db.py which runs ALTER TABLE ADD COLUMN with try/except for idempotency. For destructive changes (modifying column types, removing columns), we use fix_db.py which DROP+CREATEs all tables — but this is only used in development, never in production. In a production environment, we would implement proper versioned migrations using a tool like Alembic (SQLAlchemy's official migration framework), which tracks migration history and supports rollbacks.

Q: "What would you improve about the database design?"

A: Five improvements: (1) Add database indexes on trades.account_id and trades.status for faster queries (currently only id columns are indexed). (2) Use Numeric type instead of Float for all price columns to eliminate floating-point precision issues. (3) Add an updated_at column to accounts and trades for better audit trails. (4) Implement Alembic for proper versioned migrations with rollback capability. (5) Add a separate price_history table per symbol instead of the generic bitcoin_prices table, enabling efficient historical analysis for any asset.

Q: "How does the database handle concurrent access from the bot and API?"

A: PostgreSQL uses MVCC (Multi-Version Concurrency Control). When the bot engine updates a trade's current_price (UPDATE), it doesn't lock the row. Instead, PostgreSQL creates a new version of that row. The API server reading the same row sees the old version until the bot's transaction commits. This means reads never block writes and writes never block reads — both the bot and API can operate simultaneously without deadlocks or data corruption. SQLAlchemy's connection pool manages the underlying TCP connections, and each process gets its own session with its own transaction isolation.
