Project Overview & Your Role as Backend Engineer

What the Backend Does

The backend is the brain and nervous system of the entire QuantTrading platform. It does everything the user CANNOT see: authenticating users, connecting to the database, running the autonomous trading bot 24/7, fetching live market prices, running AI sentiment analysis, executing trades, managing risk, computing portfolio statistics, and serving all this data to the frontend through API endpoints.

Your Role: Backend & Engineering

As the Backend Engineer, you were responsible for:

  • FastAPI REST API — 15+ endpoints serving data to the frontend
  • Authentication system — JWT-based auth with bcrypt password hashing + Google OAuth
  • Bot Engine — The autonomous trading bot with 3-speed loop architecture
  • 3-Layer Verification System — Technical Analysis + FinBERT Sentiment + Quantitative Analysis
  • Data ingestion — Live prices from yfinance + news from NewsAPI + RSS feeds
  • AI/ML pipeline — FinBERT model loading, inference, and lazy caching
  • Trade execution — Position sizing, stop-loss/take-profit, risk management
  • Email reporting — Automated daily SMTP email reports
  • Networking & Hosting — Docker containerization, nginx reverse proxy, cloud deployment
  • DevOps scripts — start.sh, deploy.sh, push_to_github.sh

How Your Work Connects to Other Roles

With the Frontend Person: Every endpoint you create in main.py is consumed by an axios call in the React frontend. You define the JSON response shape; they build UI around it. You handle authentication; they send the JWT token in headers.

With the Database Person: You write SQLAlchemy queries against the tables they designed. When you call session.query(Trade).filter(...), you're querying table schemas they defined in init_db.py. You import their ORM models and use them throughout your code.

Database Dependency Injection

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

Why yield? This is FastAPI's dependency injection pattern. Every endpoint that needs database access declares db: Session = Depends(get_db). FastAPI calls get_db(), creates a session, yields it to the endpoint function, and after the endpoint returns (or raises an error), the finally block closes the session. This prevents database connection leaks.

def create_access_token(data: dict):
    to_encode = data.copy()
    expire = datetime.utcnow() + timedelta(days=30)  # 30-day expiry
    to_encode.update({"exp": expire})
    encoded_jwt = jwt.encode(to_encode, SECRET_KEY, algorithm="HS256")

Why HS256? HMAC-SHA256 is a symmetric signing algorithm. The same SECRET_KEY is used to both sign and verify tokens. This is simpler than RS256 (asymmetric) and appropriate for single-server deployments.

import os

load_dotenv()

# Build the PostgreSQL connection URL from environment variables
DB_USER = os.getenv("DB_USER", "niiamas")
DB_PASS = os.getenv("DB_PASS", "")
DB_HOST = os.getenv("DB_HOST", "localhost")
DB_NAME = os.getenv("DB_NAME", "quant_db")

# Support both individual vars and full DATABASE_URL (for Docker)
DATABASE_URL = os.getenv("DATABASE_URL",
    f"postgresql://{DB_USER}:{DB_PASS}@{DB_HOST}/{DB_NAME}")

# Create the SQLAlchemy engine with connection pooling
engine = create_engine(
    DATABASE_URL,
    pool_size=5,          # Keep 5 connections ready
    max_overflow=10,      # Allow 10 extra during spikes
    pool_pre_ping=True    # Test connections before using (handles DB restarts)
)

SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)

Connection pooling explained:

  • pool_size=5 — SQLAlchemy maintains 5 persistent connections to PostgreSQL. These are reused across requests, avoiding the overhead of creating new connections.
  • max_overflow=10 — During traffic spikes, up to 10 additional temporary connections can be created (total max: 15).
  • pool_pre_ping=True — Before using a pooled connection, SQLAlchemy sends a lightweight query (SELECT 1) to check if it's still alive. This handles cases where PostgreSQL restarted.

Architecture: 3-Speed Loop

# The main loop — runs forever until killed
while True:
    # ─── FAST LOOP (every 60 seconds) ───
    # Update live prices for all tracked symbols
    fast_cycle(session)

    # ─── MEDIUM LOOP (every 5 minutes) ───
    if cycles_since_medium >= 5:
        medium_cycle(session)     # Run 3-Layer Verification + Execute Trades
        cycles_since_medium = 0

    # ─── SLOW LOOP (every 15 minutes) ───
    if cycles_since_slow >= 15:
        slow_cycle(session)       # Fetch fresh news + AI analysis
        cycles_since_slow = 0

    time.sleep(60)  # Base tick: 60 seconds

Why 3 speeds?

  • Fast (60s): Price updates need to be frequent for accurate P&L calculations. The frontend polls every 5 seconds, so stale prices = stale portfolio values.
  • Medium (5min): Trade decisions don't need to be made every second. 5-minute intervals give enough time for price movements to develop meaningful patterns while avoiding over-trading.
  • Slow (15min): News API has a free-tier limit of 100 requests/day. At 15-minute intervals, that's 96 requests/day — just under the limit. The AI analysis is also CPU-intensive, so spacing it out prevents overload.

Fast Cycle: fast_cycle(session)

def fast_cycle(session):
    """Update live prices for every tracked symbol across all accounts."""
    accounts = session.query(Account).all()
    all_symbols = set()
    for account in accounts:
        assets = session.query(PortfolioAsset).filter(
            PortfolioAsset.account_id == account.id, PortfolioAsset.shares > 0
        ).all()
        for asset in assets:
            all_symbols.add(asset.symbol)
    
    # Batch-fetch prices from yfinance
    prices = data_ingestion.get_bulk_prices(list(all_symbols))
    
    # Update each asset's current_price in the database
    for symbol, price in prices.items():
        session.query(PortfolioAsset).filter(
            PortfolioAsset.symbol == symbol
        ).update({"current_price": price})

Medium Cycle: medium_cycle(session)

trade_executor.py — 3-Layer Verification & Trade Logic

trade_executor.py — 550+ lines — The Decision Engine

Risk Profiles

RISK_PROFILES = {
    "Low":        {"position_pct": 0.05, "sl_mult": 1.0, "tp_mult": 1.5, "min_layers": 3},
    "Moderate":   {"position_pct": 0.08, "sl_mult": 1.5, "tp_mult": 2.5, "min_layers": 2},
    "Aggressive":  {"position_pct": 0.12, "sl_mult": 2.5, "tp_mult": 4.0, "min_layers": 2},
}

What each parameter means:

  • position_pct — How much of the account balance to risk per trade (5%, 8%, or 12%)
  • sl_mult — Stop-loss multiplier based on ATR (Average True Range). Higher = wider stop, less likely to get stopped out but larger potential loss
  • tp_mult — Take-profit multiplier. Higher = larger target, but less likely to be reached
  • min_layers — Minimum number of verification layers that must pass. Low risk requires ALL 3 layers; Moderate and Aggressive need 2/3

The 3-Layer Verification Process

def run_3_layer_verification(symbol, direction):
    """
    Layer 1: Technical Analysis (TA)
      → Checks RSI, MACD, Bollinger Bands, SMA crossover
      → Returns: BULLISH, BEARISH, or NEUTRAL with confidence
    
    Layer 2: Sentiment Analysis (SA)
      → Runs FinBERT AI on recent news headlines for this symbol
      → Returns: BUY, SELL, or HOLD with confidence
    
    Layer 3: Quantitative Analysis (QA)
      → Calculates volatility, ATR, momentum, Sharpe ratio, R:R ratio
      → Returns: FAVORABLE, UNFAVORABLE, or NEUTRAL with confidence
    """
    ta_result = technical_analysis(symbol)     # Layer 1
    sa_result = ai_analysis.analyze(symbol)    # Layer 2
    qa_result = quantitative_analysis.analyze(symbol, direction)  # Layer 3
    
    # Count how many layers agree with the proposed trade
    passed = 0
    if ta_result matches direction: passed += 1
    if sa_result matches direction: passed += 1
    if qa_result matches direction: passed += 1
    
    return passed  # Must be >= min_layers to execute

Position Sizing Formula

# How much money to put into a trade
position_size = account.balance * RISK_PROFILES[strategy]["position_pct"]
# Example: $10,000 balance × 8% = $800 per trade position

# How many shares/coins to buy
shares = position_size / current_price
# Example: $800 / $150.00 per share = 5.33 shares of AAPL

Stop-Loss & Take-Profit Calculation

# Stop-loss = entry price - (ATR × sl_mult)
stop_loss = entry_price - (atr * risk_profile["sl_mult"])

# Take-profit = entry price + (ATR × tp_mult)
take_profit = entry_price + (atr * risk_profile["tp_mult"])

Why ATR-based? ATR (Average True Range) measures how much the price typically moves in a day. Using ATR-based stops adapts to each asset's volatility. A volatile crypto like BTC might have an ATR of $2,000, while a stable stock like JNJ might have an ATR of $1.50. Fixed dollar stops wouldn't work across such different assets.

def get_bulk_prices(symbols: list) -> dict:
    """Fetch current prices for multiple symbols at once."""
    prices = {}
    for symbol in symbols:
        try:
            ticker = yf.Ticker(symbol)
            hist = ticker.history(period="1d")
            if not hist.empty:
                prices[symbol] = hist["Close"].iloc[-1]
        except Exception as e:
            logger.warning(f"Price fetch failed for {symbol}: {e}")
    return prices

ai_analysis.py — FinBERT Sentiment Analysis Engine

ai_analysis.py — The AI Brain

Lazy Model Loading

_tokenizer = None
_model = None

def _load_model():
    """Load FinBERT model ONLY when first needed (saves ~2GB RAM at startup)."""
    global _tokenizer, _model
    if _tokenizer is None:
        logger.info("🧠 Loading FinBERT model (first time — this takes 30-60 seconds)...")
        _tokenizer = AutoTokenizer.from_pretrained("ProsusAI/finbert")
        _model = AutoModelForSequenceClassification.from_pretrained("ProsusAI/finbert")
        _model.eval()  # Set to inference mode (no gradient computation)
        logger.info("✅ FinBERT loaded successfully!")
    return _tokenizer, _model

Why lazy loading? FinBERT uses ~2GB RAM. If we loaded it at startup, the API server would take 60+ seconds to start and immediately consume 2GB. With lazy loading, the model loads only when the first sentiment analysis request comes in (during the slow cycle). The global variables _tokenizer and _model persist across function calls, so the model is loaded exactly once.

Sentiment Inference

def analyze_sentiment(text: str) -> dict:
    tokenizer, model = _load_model()
    
    # Tokenize the text (convert words to numbers)
    inputs = tokenizer(text, return_tensors="pt", truncation=True, max_length=512)
    
    # Run through the neural network (no gradients needed for inference)
    with torch.no_grad():
        outputs = model(**inputs)
    
    # Convert logits to probabilities with softmax
    probs = torch.nn.functional.softmax(outputs.logits, dim=-1)
    
    # FinBERT labels: [positive, negative, neutral]
    labels = ["positive", "negative", "neutral"]
    scores = probs[0].tolist()
    
    # Return the highest-confidence label
    max_idx = scores.index(max(scores))
    return {
        "label": labels[max_idx],        # "positive" or "negative"
        "score": scores[max_idx],         # 0.0 to 1.0 confidence
        "all_scores": dict(zip(labels, scores))
    }

Step-by-step inference pipeline:

  1. Tokenization: Converts "Apple stock surges on AI chip news" into numerical token IDs that the neural network understands
  2. Forward pass: The FinBERT model (12 layers of transformer attention) processes the tokens and outputs raw logit scores
  3. Softmax: Converts raw logits into probability distribution (sums to 1.0)
  4. Classification: The highest probability determines the sentiment label

torch.no_grad() — Disables gradient computation during inference. During training, PyTorch tracks gradients for backpropagation. During inference, we don't need gradients, so disabling them saves ~50% memory and speeds up computation.

quantitative_analysis.py — Statistical Math Engine

quantitative_analysis.py — Layer 3 of 3-Layer Verification

This module uses pure mathematics and statistics to evaluate if a trade setup has a favorable risk/reward profile. It calculates 7 metrics:

1. Volatility (Standard Deviation of Returns)

def _calculate_volatility(closes, period=20):
    returns = np.diff(closes) / closes[:-1]  # Daily % changes
    return float(np.std(returns[-period:]))   # Std dev of last 20 days

What it measures: How much the price fluctuates day-to-day. Low volatility (<1.5%) = stable, good for conservative trades. High volatility (>5%) = risky, needs wider stop-losses.

2. ATR (Average True Range)

def _calculate_atr(highs, lows, closes, period=14):
    for i in range(1, period + 1):
        tr = max(
            highs[-i] - lows[-i],            # Today's range
            abs(highs[-i] - closes[-i-1]),    # Gap up
            abs(lows[-i] - closes[-i-1])      # Gap down
        )
    return np.mean(tr_list)

Why 3 components? True Range captures gaps (when today's open is far from yesterday's close), which simple High-Low range misses.

3. Sharpe Ratio

def _calculate_sharpe_ratio(closes, period=30, risk_free_rate=0.05):
    returns = np.diff(closes[-period:]) / closes[-period:-1]
    excess_return = np.mean(returns) - (risk_free_rate / 252)  # Daily risk-free rate
    return excess_return / np.std(returns) * np.sqrt(252)       # Annualized

Formula: Sharpe = (Return - Risk-Free Rate) / Standard Deviation. A Sharpe > 1.0 means excellent risk-adjusted returns. We annualize by multiplying by √252 (trading days per year). The risk-free rate is 5% (current US Treasury yield).

4. Mean Reversion Z-Score

def _mean_reversion_score(closes, period=50):
    mean = np.mean(closes[-period:])
    std = np.std(closes[-period:])
    return (closes[-1] - mean) / std  # How many std devs from mean

Trading logic: Z-score < -1.5 = price is far below average → potential bounce up (good for BUY). Z-score > 1.5 = price is far above average → potential pullback (good for SELL).

Scoring System

# Each metric produces a score from -0.7 to +0.7
# The average of all 7 scores determines the verdict:
if avg_score > 0.15:  verdict = "FAVORABLE"     # Math supports the trade
elif avg_score < -0.15: verdict = "UNFAVORABLE"  # Math is against the trade
else: verdict = "NEUTRAL"                         # Inconclusive — soft pass

How requests flow:

  1. User visits http://your-server-ip → hits nginx on port 80
  2. Nginx serves static React files from /usr/share/nginx/html
  3. React code makes API calls to /accounts, /news, etc.
  4. Nginx sees these paths and proxies them to the backend container on port 8000
  5. FastAPI processes the request, queries PostgreSQL on port 5432
  6. Response flows back: PostgreSQL → FastAPI → Nginx → Browser
nginx.conf — Reverse Proxy Configuration
server {
    listen 80;
    server_name _;

    # Serve frontend static files (React build output)
    root /usr/share/nginx/html;
    index index.html;

    # SPA routing — all non-file URLs go to index.html
    location / {
        try_files $uri $uri/ /index.html;
    }

    # Proxy API requests to the backend container
    location /api/ {
        proxy_pass http://backend:8000/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }

    # Also proxy direct backend paths
    location ~ ^/(accounts|auth|signal|prices|explorer|news|bot)(/|$) {
        proxy_pass http://backend:8000;
    }
}

Key concept — try_files $uri $uri/ /index.html: This is critical for Single Page Applications. When a user navigates to /trading-hub, nginx doesn't have a file at that path. Without this directive, nginx returns 404. With it, nginx falls back to index.html, which loads React, which reads the URL and renders the correct page.

proxy_pass http://backend:8000: In Docker Compose, services can reference each other by name. backend resolves to the backend container's IP address via Docker's internal DNS.

Key Defense Q&A

Common Questions & Perfect Answers

Q: "Why FastAPI over Django or Flask?"

A: FastAPI was chosen for 3 reasons: (1) Performance — it's the fastest Python framework, built on ASGI/Starlette, capable of handling thousands of concurrent requests. Our polling-based frontend makes ~720 requests/hour per active user (every 5 seconds), so performance matters. (2) Automatic API documentation — FastAPI generates Swagger UI at /docs, which helped the Frontend developer understand our endpoints without a separate spec document. (3) Built-in data validation via Pydantic — every request is automatically validated, reducing bugs.

Q: "Explain the 3-Layer Verification System."

A: Before executing any trade, the bot runs 3 independent analysis layers: (1) Technical Analysis checks price patterns (RSI for overbought/oversold, MACD for momentum, Bollinger Bands for volatility, SMA crossovers for trend). (2) Sentiment Analysis runs our FinBERT AI model on recent news headlines for the symbol, classifying them as positive/negative/neutral. (3) Quantitative Analysis computes statistical metrics (volatility, Sharpe ratio, risk/reward ratio, mean reversion z-score). Each layer votes independently. For Moderate risk, at least 2 of 3 layers must agree. For Low risk, all 3 must agree. This multi-layer approach prevents the bot from making decisions based on a single biased signal.

Q: "How does the bot manage risk?"

A: Five risk controls: (1) Position sizing — never risk more than 5-12% of account balance per trade. (2) ATR-based stop-losses — automatically calculated for each asset's volatility. (3) Take-profit targets — ATR-based targets ensure we lock in profits. (4) Maximum drawdown protection — if the portfolio drops by the configured percentage in a day, all trading halts. (5) The 3-Layer Verification gate — trades are only executed when multiple independent analyses agree.

Q: "Why Docker for deployment?"

A: Docker ensures our application runs identically in development and production. The Python version, library versions, and system dependencies are frozen in the Dockerfile. Without Docker, deploying to Oracle Cloud would require manually installing Python 3.11, PostgreSQL, gcc, libpq-dev, Node.js, and all pip/npm packages — any version mismatch could cause failures. Docker Compose orchestrates 3 containers (db, backend, frontend) with a single docker compose up -d command.

Q: "How does the backend handle concurrent database access?"

A: SQLAlchemy's connection pool manages this. We configured pool_size=5 with max_overflow=10, allowing up to 15 concurrent database connections. The API server and bot engine run as separate processes, each getting their own connection from the pool. PostgreSQL handles concurrent transactions with MVCC (Multi-Version Concurrency Control), so the bot can write new trades while the API reads portfolio data simultaneously.
